## What is Fetch?

The Fetch interaction allows you to execute pre-configured API requests that you've stored in Autonoma's database. Think of it as a way to save complex API calls—complete with headers, authentication, request bodies, and more—and trigger them with a simple natural language command during your tests.

Instead of manually configuring the same API call repeatedly across multiple tests, you define it once as a named script (like "SCRIPT_1" or "GET_USER_PROFILE") and then execute it whenever needed with a simple prompt.

This is particularly powerful for:
- Testing API integrations within your application
- Validating that your UI correctly triggers backend calls
- Seeding test data before UI interactions
- Verifying API responses affect the UI as expected
- Testing error handling when APIs return specific responses

## When to Use Fetch vs Other Approaches

Understanding when to use Fetch versus other methods is crucial for building maintainable test suites.

### Use Fetch when:

**Testing API-driven UI updates**
```
Your application makes an API call when a user clicks "Refresh Balance"
You want to verify the UI updates correctly with the API response
```

**Seeding data before UI tests**
```
Before testing the order history page, use Fetch to create test orders via API
Then verify they appear correctly in the UI
```

**Testing error handling**
```
Use Fetch to trigger API error responses
Verify your application displays appropriate error messages
```

**Validating API integration**
```
User submits a form
Use Fetch to verify the correct API call was made with proper data
```

**Reusing complex API calls across tests**
```
Multiple tests need to authenticate or fetch user data
Store the API call once, execute it in all tests that need it
```

### Use alternatives when:

**Testing pure UI interactions**
```
If you're not testing API behavior, you don't need Fetch
Use standard interactions like Click, Input Text, Assert
```

**One-off API calls**
```
If you only need an API call once, consider using cURL interaction
Or configure it directly in your test setup
```

**External API testing**
```
If you're testing third-party APIs without UI validation
Consider using dedicated API testing tools
```

**Real-time data that changes constantly**
```
If the API response varies unpredictably
Fetch might not provide the control you need
```

## Fetch vs cURL: What's the Difference?

Both Fetch and cURL interactions execute HTTP requests, but they serve different purposes:

### Fetch (JavaScript Fetch API style)

**Best for:**
- Modern RESTful APIs
- JSON request/response patterns
- Standard authentication patterns (Bearer tokens, API keys)
- Promise-based async operations
- CORS-aware requests

**Example use cases:**
```
Fetch user profile data from your REST API
Post form data in JSON format
Retrieve paginated results
Update resources with PUT/PATCH requests
```

### cURL (Command-line style)

**Best for:**
- Complex HTTP scenarios requiring fine-grained control
- Custom headers or unusual configurations
- Binary data or file uploads
- Legacy systems with non-standard patterns
- Debugging and exploring APIs

**Example use cases:**
```
Testing APIs with custom authentication schemes
Uploading files via multipart/form-data
Making requests with very specific header requirements
Replicating exact cURL commands from documentation
```

**Rule of thumb**: Start with Fetch for standard REST APIs. Use cURL when you need command-line-level control or are replicating existing cURL commands.

## How It Works

When you use the Fetch interaction, here's what happens:

1. **Script Lookup**: Autonoma retrieves the named fetch script from your account's stored scripts
2. **Configuration Loading**: The script contains all request details (URL, method, headers, body, auth)
3. **Request Execution**: Autonoma executes the fetch request using the configured parameters
4. **Response Handling**: The response is captured and can be used in subsequent test steps
5. **Validation**: You can verify the response or check how it affects your application

### Typical Fetch Script Structure

A fetch script you've stored might look like this:

```javascript
{
  "name": "GET_USER_PROFILE",
  "method": "GET",
  "url": "https://api.example.com/users/profile",
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}",
    "Content-Type": "application/json"
  }
}
```

When you execute this with "use GET_USER_PROFILE to fetch data", Autonoma runs this exact configuration.

## Setting Up Fetch Scripts

Before using Fetch in your tests, you need to configure your scripts in Autonoma. Here's how to structure effective fetch scripts:

### Basic Fetch Script Structure

```javascript
{
  "name": "DESCRIPTIVE_SCRIPT_NAME",
  "method": "GET|POST|PUT|PATCH|DELETE",
  "url": "https://api.example.com/endpoint",
  "headers": {
    "Authorization": "Bearer token_here",
    "Content-Type": "application/json"
  },
  "body": {
    // For POST/PUT/PATCH requests
  }
}
```

### Using Variables in Fetch Scripts

Make your scripts flexible with variables:

```javascript
{
  "name": "GET_USER_ORDERS",
  "method": "GET",
  "url": "{{variable:API_BASE_URL}}/users/{{key:USER_ID}}/orders",
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}",
    "Content-Type": "application/json"
  }
}
```

This script uses:
- `{{variable:API_BASE_URL}}` - Set before test runs (staging vs production)
- `{{key:USER_ID}}` - Extracted during test execution
- `{{variable:AUTH_TOKEN}}` - Authentication token from test configuration

### Common Fetch Script Patterns

**GET request with authentication:**
```javascript
{
  "name": "GET_USER_PROFILE",
  "method": "GET",
  "url": "{{variable:API_URL}}/profile",
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}"
  }
}
```

**POST request with JSON body:**
```javascript
{
  "name": "CREATE_ORDER",
  "method": "POST",
  "url": "{{variable:API_URL}}/orders",
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}",
    "Content-Type": "application/json"
  },
  "body": {
    "items": [
      {"productId": "{{key:PRODUCT_ID}}", "quantity": 1}
    ],
    "shippingAddress": {
      "street": "{{variable:TEST_ADDRESS}}",
      "city": "{{variable:TEST_CITY}}"
    }
  }
}
```

**PUT request to update resource:**
```javascript
{
  "name": "UPDATE_USER_EMAIL",
  "method": "PUT",
  "url": "{{variable:API_URL}}/users/{{key:USER_ID}}",
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}",
    "Content-Type": "application/json"
  },
  "body": {
    "email": "{{random:email}}"
  }
}
```

**DELETE request:**
```javascript
{
  "name": "DELETE_CART_ITEM",
  "method": "DELETE",
  "url": "{{variable:API_URL}}/cart/{{key:ITEM_ID}}",
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}"
  }
}
```

## Best Practices

### 1. Use Descriptive Script Names

**Poor naming:**
```
SCRIPT_1
SCRIPT_2
TEST_API
API_CALL
```

**Good naming:**
```
GET_USER_PROFILE
CREATE_TEST_ORDER
UPDATE_SHIPPING_ADDRESS
DELETE_CART_CONTENTS
VERIFY_PAYMENT_METHOD
```

Descriptive names make your tests self-documenting and easier to maintain.

### 2. Store Commonly Used API Calls

If multiple tests need the same API call, create a fetch script:

**Instead of:**
```
Configuring the same API call in 15 different tests
```

**Do this:**
```
Create one fetch script named "GET_USER_SETTINGS"
Use it across all 15 tests with one line:
"execute the fetch command called GET_USER_SETTINGS"
```

### 3. Use Variables for Flexibility

Make scripts work across environments:

```javascript
{
  "name": "GET_ORDERS",
  "url": "{{variable:API_BASE_URL}}/orders", // Not hardcoded!
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}" // Not hardcoded!
  }
}
```

Then configure variables per environment:
- Staging: `API_BASE_URL = https://staging-api.example.com`
- Production: `API_BASE_URL = https://api.example.com`

### 4. Combine with Extraction for Validation

Always extract and verify API responses:

```
1. Execute the fetch command called GET_BALANCE
2. Extract information about balance from response with key API_BALANCE
3. Extract information about displayed balance with key UI_BALANCE
4. Assert: UI balance {{key:UI_BALANCE}} matches API balance {{key:API_BALANCE}}
```

### 5. Use Fetch for Test Setup

Speed up tests by using APIs to set up initial state:

```
Test: "Edit existing order"

Setup via API:
1. Execute the fetch command called CREATE_TEST_ORDER
2. Extract information about order ID with key ORDER_ID

Test via UI:
3. Navigate to order history
4. Click order {{key:ORDER_ID}}
5. Click "Edit Order"
6. Update order details
7. Save changes

Verify via API:
8. Execute the fetch command called GET_ORDER_DETAILS
9. Verify changes persisted
```

This is faster than creating orders through the UI.

### 6. Handle Authentication Properly

Store auth tokens securely in variables:

```javascript
{
  "headers": {
    "Authorization": "Bearer {{variable:AUTH_TOKEN}}" // From secure variable
  }
}
```

Never hardcode tokens in fetch scripts.

### 7. Test Both Success and Failure Scenarios

Create fetch scripts for different response scenarios:

```
Scripts:
- GET_PRODUCTS_SUCCESS (returns 200 with products)
- GET_PRODUCTS_EMPTY (returns 200 with empty array)
- GET_PRODUCTS_ERROR (returns 500 error)
- GET_PRODUCTS_UNAUTHORIZED (returns 401)
```

Then test how your UI handles each:

```
Test: "Handle API errors gracefully"
1. Execute the fetch command called GET_PRODUCTS_ERROR
2. Assert: Error message displays
3. Assert: Retry button is available
```

## Common Pitfalls

### Pitfall 1: Not Extracting Response Data

**Problem:**
```
1. Execute the fetch command called GET_USER_PROFILE
2. Assert: Profile page looks correct
```

You executed the API but didn't verify the response or extract useful data.

**Solution:**
```
1. Execute the fetch command called GET_USER_PROFILE
2. Extract information about username from response with key USERNAME
3. Extract information about email from response with key EMAIL
4. Navigate to profile page
5. Assert: Username {{key:USERNAME}} is displayed
6. Assert: Email {{key:EMAIL}} is displayed
```

### Pitfall 2: Hardcoding Environment-Specific URLs

**Problem:**
```javascript
{
  "name": "GET_ORDERS",
  "url": "https://staging-api.example.com/orders" // Hardcoded!
}
```

This script only works in staging. It will fail in production.

**Solution:**
```javascript
{
  "name": "GET_ORDERS",
  "url": "{{variable:API_BASE_URL}}/orders" // Flexible!
}
```

### Pitfall 3: Not Handling Async Responses

**Problem:**
```
1. Execute the fetch command called CREATE_ORDER
2. Assert: Order appears in UI immediately
```

API might not have finished, or UI might not have refreshed yet.

**Solution:**
```
1. Execute the fetch command called CREATE_ORDER
2. Extract information about order ID with key ORDER_ID
3. Wait until: Order {{key:ORDER_ID}} appears in UI
4. Assert: Order is visible
```

### Pitfall 4: Overusing Fetch for UI Testing

**Problem:**
```
Test: "Complete checkout flow"
1. Execute fetch to add items to cart
2. Execute fetch to apply discount
3. Execute fetch to set shipping
4. Execute fetch to place order
5. Verify order confirmation appears
```

This tests the API, not the UI. Users don't interact with APIs directly.

**Solution:**
```
Test: "Complete checkout flow"
1. Navigate to products
2. Click "Add to Cart" on product
3. Click cart icon
4. Click "Proceed to Checkout"
5. Fill out shipping form
6. Click "Place Order"
7. Extract information about order ID with key ORDER_ID
8. Execute fetch called VERIFY_ORDER_CREATED to confirm backend state
```

Test the UI primarily, use Fetch to verify backend state.

### Pitfall 5: Not Handling Rate Limits

**Problem:**
```
Loop 100 times:
  Execute the fetch command called GET_PRODUCTS
```

You'll hit rate limits and tests will fail.

**Solution:**
```
Add appropriate waits between API calls
Consider batching operations
Use API pagination instead of repeated calls
```

### Pitfall 6: Ignoring Response Status Codes

**Problem:**
```
1. Execute the fetch command called UPDATE_PROFILE
2. Assume it succeeded
3. Navigate to profile page
```

The API might have returned an error, but you didn't check.

**Solution:**
```
1. Execute the fetch command called UPDATE_PROFILE
2. Extract information about response status with key API_STATUS
3. Assert: Status {{key:API_STATUS}} is "200" or "204"
4. Navigate to profile page
5. Verify changes applied
```

## Debugging Fetch Issues

### Common Error: Script Not Found

**Error message:**
```
Failed to execute fetch command: Script "GET_USER_DATA" not found
```

**Causes:**
- Script name typo in your test
- Script not created in Autonoma
- Script name case mismatch

**Solution:**
```
1. Verify script name exactly matches what you stored
2. Check script exists in your Autonoma account
3. Ensure case matches (GET_USER_DATA vs get_user_data)
```

### Common Error: Authentication Failed

**Error message:**
```
Fetch request failed with 401 Unauthorized
```

**Causes:**
- Auth token expired or invalid
- Token not properly included in headers
- Variable containing token is empty

**Solution:**
```
1. Verify {{variable:AUTH_TOKEN}} is set correctly
2. Check token hasn't expired
3. Ensure token is included in Authorization header
4. Test the API call manually with the token
```

### Common Error: Request Timeout

**Error message:**
```
Fetch request timed out after 30 seconds
```

**Causes:**
- API endpoint is slow or unresponsive
- Network connectivity issues
- Wrong URL configured

**Solution:**
```
1. Test API endpoint manually
2. Check API URL is correct
3. Verify network connectivity
4. Consider increasing timeout if API is legitimately slow
```

### Common Error: Invalid Response Format

**Error message:**
```
Failed to parse response: Unexpected token < in JSON
```

**Causes:**
- API returned HTML instead of JSON (usually error page)
- API URL is incorrect
- Authentication failed and returned login page

**Solution:**
```
1. Check API URL is correct
2. Verify authentication is working
3. Test API endpoint manually to see actual response
4. Ensure Content-Type headers are correct
```
