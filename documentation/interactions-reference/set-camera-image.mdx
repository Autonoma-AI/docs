## What is Set Camera Image?

Set Camera Image is Autonoma's solution for testing mobile app features that use the device camera. It's the mobile equivalent of file uploads, but specifically designed for camera capture workflows.

Think of it as giving your automated test the ability to "take a photo" without needing an actual camera. When your mobile app opens the camera to capture a profile picture, scan a document, or take a product photo, Set Camera Image provides a pre-selected image as if the user took that photo with their device's camera.

What makes this powerful is that it eliminates the complexity of simulating physical camera hardware. Traditional mobile testing requires either physical devices with cameras or complex emulator camera configurations. Set Camera Image sidesteps this entirely by intercepting the camera request and providing a pre-loaded image—the test flows naturally as if a user captured a photo.

## When to Use Set Camera Image

Set Camera Image should be used whenever your mobile app test needs to simulate camera capture. Here's when it's the right tool:

**Perfect for:**
- Profile picture capture ("Take Photo" button in profile screens)
- Product photo uploads in marketplace apps
- Document scanning features (ID verification, receipts)
- Social media photo posting
- AR features that require camera input
- Photo-based authentication (selfie verification)
- Image-based search features (visual product search)
- QR code scanning (when combined with QR code images)
- Real estate listing photos
- Food delivery app dish photos

**Required when:**
- Your mobile app opens the device camera
- Users tap "Take Photo" or "Capture Image" buttons
- Camera permission is granted and camera view opens
- You need to test the complete camera capture flow
- Your app processes captured photos (filters, cropping, recognition)

**Not needed when:**
- Testing web applications (use Set File to Upload instead)
- App uses photo library/gallery selection (may work, but not primary use case)
- Desktop application testing
- Features that don't involve image capture

## How It Works

When you use Set Camera Image in Autonoma, here's the complete process:

1. **Image Selection**: You provide a URL to an image (hosted online or local)
2. **Image Loading**: Autonoma fetches and stores the image in memory
3. **Camera Interception**: When your test triggers camera functionality, Autonoma intercepts the camera call
4. **Image Provision**: The pre-loaded image is provided as if captured by the camera
5. **App Processing**: Your application receives the image exactly as it would from an actual camera capture
6. **Workflow Continuation**: The test continues with the captured image in place
7. **Image Persistence**: The image remains available until you unset it or the test ends

From your mobile app's perspective, a user opened the camera, took a photo, and confirmed the capture. The app has no way to distinguish this from a real camera interaction.

## Platform Support

- **Web**: Not supported (use Set File to Upload for web file uploads)
- **Mobile**: Full support (Android and iOS)

Set Camera Image is exclusively for mobile application testing where camera capture is involved.

## Image URL Specifications

Set Camera Image requires a URL to the image you want to use. Understanding the correct URL format and hosting options is crucial.

### URL Format Options

**Hosted image URL (recommended):**
```
https://example.com/test-assets/profile-photo.jpg
https://storage.googleapis.com/test-images/receipt.png
https://s3.amazonaws.com/qa-files/document.jpg
```

**Local file URL (if supported):**
```
file:///storage/emulated/0/Pictures/test-image.jpg
```

**Important considerations:**
- URLs must be accessible from the test environment
- Images should be hosted on reliable servers
- HTTPS is recommended for security
- Image must be in a supported format (JPG, PNG, WebP)

### Hosting Test Images

**Option 1: Project repository**
Commit test images to your code repository and serve them during tests:

```
your-project/
  ├── tests/
  └── test-assets/
      └── images/
          ├── profile-photo.jpg
          ├── drivers-license-sample.jpg
          ├── receipt-template.jpg
          └── product-photo.jpg
```

Then host via a local server or use direct URLs if your test environment supports it.

**Option 2: Cloud storage**
Upload test images to cloud storage (S3, Google Cloud Storage, Azure Blob Storage):

```
https://your-bucket.s3.amazonaws.com/test-images/profile-photo.jpg
https://storage.googleapis.com/your-bucket/test-images/receipt.jpg
```

**Benefits:**
- Reliable access from any test environment
- Easy to share across team
- Works in CI/CD without special configuration

**Option 3: CDN or asset server**
Host test images on a CDN or dedicated test asset server:

```
https://cdn.yourdomain.com/test-assets/profile-photo.jpg
https://test-assets.yourdomain.com/images/receipt.jpg
```

### Image Specifications

**Recommended image properties:**
- **Format**: JPG or PNG (WebP if supported)
- **Size**: 1-3MB (realistic phone camera size)
- **Dimensions**:
  - Profile photos: 800x800px to 1200x1200px
  - Document scans: 2000x1500px or higher
  - Product photos: 1200x1200px to 1600x1600px
  - Receipts: 1000x1500px or higher
- **Quality**: Good enough to be realistic, not so high that it slows tests

**Aspect ratios:**
- Portrait: 3:4 (common for document scans)
- Square: 1:1 (common for profile pictures)
- Landscape: 4:3 (common for general photos)

## Best Practices

### 1. Set Camera Image Before Opening Camera

Always set the camera image before your test clicks the button that opens the camera.

**Good:**
```
1. Navigate to profile screen
2. Set camera image: https://example.com/profile-photo.jpg
3. Click "Take Photo" button
4. Wait until: Photo captured
```

**Wrong order:**
```
1. Navigate to profile screen
2. Click "Take Photo" button ← Opens camera first
3. Set camera image: https://example.com/profile-photo.jpg ← Too late
```

### 2. Use Realistic Test Images

Use images that closely match what real users would capture with their cameras.

**Good test images:**
- Profile photos: Actual face photos (not logos or graphics)
- Documents: Realistic document layouts with readable text
- Receipts: Actual receipt photos with proper formatting
- Products: Clear product photos with appropriate backgrounds

**Poor test images:**
- Placeholder images or stock graphics
- Images with wrong dimensions
- Unrealistic or synthetic images
- Corrupt or invalid image files

### 3. Verify Capture Completion

Always verify that the camera capture completed successfully and the image was accepted.

**Good:**
```
1. Set camera image: https://example.com/receipt.jpg
2. Click "Scan Receipt" button
3. Wait until: Image captured
4. Wait until: Receipt preview appears
5. Verify: Receipt image is displayed
6. Verify: "Use This Photo" button is enabled
```

**Risky:**
```
1. Set camera image: https://example.com/receipt.jpg
2. Click "Scan Receipt" button
3. Click "Continue" button ← Might click before capture completes
```

### 4. Test Camera Permissions

Include camera permission handling in your tests when testing fresh app installs.

```
Test: "Grant camera permission and capture photo"

1. Launch app for first time
2. Navigate to profile setup
3. Click "Add Profile Picture" button
4. Wait until: Camera permission dialog appears
5. Click "Allow" on permission dialog
6. Wait until: Camera view opens
7. Set camera image: https://example.com/profile.jpg
8. Wait until: Photo captured
9. Verify: Photo preview appears
```

### 5. Handle Camera UI Variations

Different devices and OS versions may have different camera UI layouts. Write flexible tests:

```
# Instead of clicking precise coordinates
Click coordinates (200, 400) ← Breaks on different devices

# Use prompt-based clicks that find the shutter button
Click "Capture" button ← Works across devices
```

### 6. Clean Up After Tests

Use Unset Camera Image to clear the camera image when it's no longer needed, especially in tests with multiple camera captures:

```
Test: "Upload two different product photos"

# First photo
1. Set camera image: https://example.com/product-front.jpg
2. Click "Take Photo" button
3. Wait until: First photo added
4. Unset camera image

# Second photo
5. Set camera image: https://example.com/product-back.jpg
6. Click "Take Photo" button
7. Wait until: Second photo added
8. Unset camera image
```

### 7. Test Image Processing Features

If your app processes captured images (cropping, filters, enhancement), verify these features work with test images:

```
1. Set camera image: https://example.com/photo.jpg
2. Click "Take Photo" button
3. Wait until: Photo editor appears
4. Click "Filter" button
5. Click "Vintage" filter
6. Wait until: Filter applied to preview
7. Verify: Image shows sepia tones
8. Click "Crop" button
9. Adjust crop to square
10. Click "Apply" button
11. Verify: Cropped image preview updates
```

### 8. Use High-Quality Images for OCR Testing

When testing document scanning or receipt OCR, use high-resolution, clear images:

**Good for OCR:**
- High-resolution scans (300 DPI or higher)
- Clear, readable text
- Good lighting and contrast
- Straight, unrotated documents

**Poor for OCR:**
- Low-resolution images
- Blurry or out-of-focus photos
- Rotated or skewed documents
- Poor lighting or shadows

## Common Pitfalls

### Pitfall 1: Setting Camera Image After Opening Camera

**Problem:**
```
1. Click "Take Photo" button ← Camera opens
2. Set camera image: https://example.com/photo.jpg ← Too late
```

The camera has already opened before the image was set.

**Solution:**
```
1. Set camera image: https://example.com/photo.jpg ← Set first
2. Click "Take Photo" button ← Then open camera
```

### Pitfall 2: Using Broken or Inaccessible Image URLs

**Problem:**
```
set camera image: https://example.com/non-existent-photo.jpg
```

If this URL doesn't exist or isn't accessible, the interaction will fail.

**Solution:**
- Verify image URLs are accessible before using them in tests
- Host test images on reliable infrastructure
- Test image URLs manually in a browser first
- Use stable URLs that won't change

### Pitfall 3: Wrong Image Format or Size

**Problem:**
Using an image that's too large, wrong format, or inappropriate dimensions:
```
set camera image: https://example.com/huge-10mb-photo.tiff
```

**Solution:**
- Use standard formats (JPG, PNG)
- Keep images under 3MB
- Use realistic dimensions for mobile cameras
- Test with images similar to what real cameras produce

### Pitfall 4: Not Handling Multiple Camera Captures

**Problem:**
When an app allows multiple photo captures, forgetting to set new images for each capture:
```
1. Set camera image: https://example.com/photo1.jpg
2. Click "Add Photo 1" button
3. Click "Add Photo 2" button ← Uses same image from step 1
```

**Solution:**
Set a new camera image before each capture:
```
1. Set camera image: https://example.com/photo1.jpg
2. Click "Add Photo 1" button
3. Set camera image: https://example.com/photo2.jpg ← New image
4. Click "Add Photo 2" button
```

### Pitfall 5: Not Verifying Image Quality Requirements

**Problem:**
Your app rejects low-quality images, but your test uses a blurry or low-resolution image:
```
1. Set camera image: https://example.com/blurry-photo.jpg
2. Click "Take Photo" button
3. Error: "Image quality too low. Please retake."
```

**Solution:**
Use test images that meet your app's quality requirements. If testing validation, create separate tests for quality rejection:
```
Test: "Reject low-quality images"
1. Set camera image: https://example.com/low-quality.jpg
2. Click "Take Photo" button
3. Wait until: Error message appears
4. Verify: "Image quality too low" message is shown
```

### Pitfall 6: Ignoring Camera Permission States

**Problem:**
Test assumes camera permission is already granted when it's not:
```
1. Set camera image: https://example.com/photo.jpg
2. Click "Take Photo" button ← Permission dialog appears
3. Expecting camera to open immediately
```

**Solution:**
Handle permission dialogs in your test:
```
1. Set camera image: https://example.com/photo.jpg
2. Click "Take Photo" button
3. If permission dialog appears:
   4. Click "Allow" button
5. Wait until: Camera opens
```

### Pitfall 7: Testing Only Happy Path

**Problem:**
Only testing successful camera captures without testing edge cases:

**Solution:**
Create comprehensive test coverage:
```
Suite: Camera Capture Tests

Test 1: Successful photo capture (happy path)
Test 2: User denies camera permission
Test 3: User cancels camera without taking photo
Test 4: App rejects image due to quality
Test 5: App rejects image due to file size
Test 6: Capture multiple photos sequentially
```

## Comparison with Similar Interactions

### Set Camera Image vs Set File to Upload

**Set Camera Image:**
- Platform: Mobile only
- Use case: Camera capture simulation
- Source: URL to hosted image
- Trigger: Camera opens in app
- Best for: Mobile camera features
- File types: Images only

**Set File to Upload:**
- Platform: Web only
- Use case: File input controls
- Source: Local file system path
- Trigger: File picker dialog
- Best for: Web file uploads
- File types: Any (images, PDFs, CSVs, etc.)

**When to switch**: Use Set File to Upload for web applications. Use Set Camera Image for mobile camera functionality.

### Set Camera Image vs Unset Camera Image

**Set Camera Image:**
- Purpose: Load an image for camera capture
- When: Before opening camera
- Effect: Next camera capture uses this image
- Usage: Required for camera testing

**Unset Camera Image:**
- Purpose: Clear the loaded camera image
- When: After camera capture or between captures
- Effect: Removes the set image from memory
- Usage: Optional cleanup, useful for multiple captures

**Pattern**: Set → Use → Unset → Set → Use → Unset (for multiple photos)

### Set Camera Image vs Photo Library Selection

**Set Camera Image:**
- Simulates: Taking a new photo with camera
- Use for: "Take Photo" / "Camera" buttons
- Image processing: Full camera capture flow
- Permissions: Requires camera permission

**Photo Library (not a separate interaction):**
- Simulates: Selecting existing photo from gallery
- Use for: "Choose from Library" buttons
- May work: With Set Camera Image depending on implementation
- Permissions: Requires photo library permission

Most apps offer both options. Set Camera Image works best for the camera capture path.

## Platform-Specific Considerations

### Android Considerations

- Camera UI varies between manufacturers (Samsung, Google, OnePlus)
- Test with generic button prompts that work across brands
- Consider different camera app implementations
- Handle permission dialogs that vary by Android version

### iOS Considerations

- Consistent camera UI across devices
- Permission dialogs have standard format
- Camera controls in consistent locations
- Consider different screen sizes (iPhone SE vs Pro Max)

## Key Takeaways

1. **Mobile-only feature** - Set Camera Image is exclusively for mobile app testing
2. **Set before opening camera** - Always set the image before clicking camera buttons
3. **Use image URLs** - Provide URLs to hosted test images, not file paths
4. **Realistic test images** - Use images similar to what real cameras capture
5. **Verify capture completion** - Always wait for and verify successful capture
6. **Handle permissions** - Include camera permission granting in tests
7. **Clean up between captures** - Use Unset Camera Image when capturing multiple photos
8. **Test image processing** - Verify filters, cropping, and editing features work
9. **Host reliably** - Store test images on stable, accessible servers
10. **Test edge cases** - Include permission denial, cancelation, and rejection scenarios
