## What is Go Home?

Go Home is the mobile-specific interaction that navigates from your current app to the device's home screen. It simulates what happens when a user presses the home button (or swipes up on devices without physical buttons) to exit the app and return to their home screen.

This is fundamentally different from closing an app or navigating backward—it backgrounds the app (leaving it running in memory) while taking you to the home screen where you can launch other apps, check widgets, or perform device-level actions.

Think of it as the mobile equivalent of minimizing a desktop application. The app doesn't close or terminate; it simply moves to the background, and the device shows its home screen with all the app icons, widgets, and system UI elements.

Go Home is essential for testing scenarios where users temporarily leave your app—checking messages, answering calls, switching to another app, or pausing their activity—and then return later.

## When to Use Go Home

This interaction is designed for mobile device navigation and app backgrounding scenarios. Here's when it's the right choice:

**Perfect for:**
- Testing app backgrounding and foregrounding behavior
- Verifying that app state persists when users leave and return
- Testing push notification handling (go home, trigger notification, tap notification)
- Checking that timers or media continue playing in background
- Testing multi-app workflows (use App A, go home, open App B, go home, return to App A)
- Validating that forms or partially completed tasks save when app backgrounds
- Testing app lifecycle events (onPause, onResume, etc.)
- Verifying that authentication sessions persist across backgrounding
- Testing that location tracking continues when app is backgrounded

**Choose an alternative when:**
- You're testing web applications (use `go-back-on-page` or standard navigation)
- You want to navigate backward within the app (use app-specific back navigation)
- You want to close a browser tab (use `exit-last-tab` on web)
- You're navigating forward to a new URL (use `open-url-on-new-page` or navigation)

## Platform Support

- **Web**: Not supported (home screen concept doesn't exist in web browsers)
- **Mobile**: Full support (Android and iOS)

Go Home is exclusively a mobile interaction. It leverages the mobile device's home button functionality, which is a core pattern on smartphones and tablets but doesn't have an equivalent on web browsers.

## How It Works

When you use Go Home, here's what happens on the device:

1. **Home Action Triggered**: Autonoma simulates pressing the device home button
2. **App Backgrounds**: Your app receives background lifecycle events (onPause, onStop on Android; applicationDidEnterBackground on iOS)
3. **Home Screen Displays**: The device home screen appears with app icons and widgets
4. **App Remains in Memory**: The app continues running in background (unless OS terminates it for memory)
5. **Test Can Continue**: Your test can now perform home screen actions or relaunch apps

The critical behavior is that the app remains running in the background. This is different from force-closing or killing the app. The app's state, memory, and background processes persist (within OS limits).

## Best Practices

### 1. Wait After Going Home

The home screen takes time to appear and apps need time to background.

**Good:**
```
1. Go home
2. Wait until: Home screen appears
3. Assert: Device home screen visible
4. Continue test
```

**Risky:**
```
1. Go home
2. Click: Another app icon  ← May fail if home screen not fully loaded
```

**Why**: Backgrounding and home screen animation take time. Always wait before next action.

### 2. Verify App Backgrounded Successfully

After going home, confirm the app actually backgrounded.

**Good:**
```
1. (In app, form partially filled)
2. Go home
3. Wait until: Home screen appears
4. Assert: App icons visible
5. Assert: Not in app anymore
```

**Why**: Confirming successful backgrounding ensures your test state is correct.

### 3. Test Return to App After Backgrounding

Always test that users can successfully return to your app.

**Good test pattern:**
```
1. Perform actions in app
2. Go home (background app)
3. Wait
4. Launch app again
5. Assert: App state preserved
6. Continue workflow
```

**Why**: The complete cycle (background + return) is what users experience. Test both parts.

### 4. Test Various Background Durations

Apps may behave differently based on how long they're backgrounded.

**Test short backgrounding:**
```
1. Go home
2. Wait: 2 seconds
3. Return to app
4. Verify state preserved
```

**Test long backgrounding:**
```
1. Go home
2. Wait: 60 seconds (simulating extended interruption)
3. Return to app
4. Verify app handles potential memory pressure
```

**Why**: OS may treat short vs long backgrounding differently. Test both.

### 5. Verify Background Permissions Work

Test that permissions like location, notifications, and media work while backgrounded.

**Good:**
```
Test: "Background location permission"
1. Enable location tracking
2. Go home
3. Assert: Location icon shows in status bar
4. Wait: 10 seconds
5. Return to app
6. Assert: Location data collected while backgrounded
```

**Why**: Background permissions are critical for many app features. Explicitly test them.

### 6. Test Notification Handling from Home Screen

Go Home is essential for testing notification workflows.

**Good:**
```
1. Trigger notification in app
2. Go home
3. Wait until: Notification appears
4. Assert: Notification visible
5. Click: Notification
6. Assert: App opens to correct screen
```

**Why**: Notifications primarily appear when apps are backgrounded. Test the real flow.

## Common Pitfalls

### Pitfall 1: Assuming App State Always Persists

**Problem:**
```
1. Fill complex form
2. Go home
3. Wait: 10 minutes (OS may kill app for memory)
4. Return to app
5. Expect: Form data still there  ← May fail, app might have been killed
```

**Solution:**
```
Test different backgrounding durations
Verify app properly saves/restores state
Handle both memory preservation and cold start scenarios
```

**Why**: OS can terminate backgrounded apps. Your app needs to handle state restoration.

### Pitfall 2: Not Waiting for Home Screen to Appear

**Problem:**
```
1. Go home
2. Click: Another app  ← May fail if home screen animation not complete
```

**Solution:**
```
1. Go home
2. Wait until: Home screen fully loaded
3. Assert: Home screen visible
4. Click: Another app
```

**Why**: Home screen animation and app backgrounding take time.

### Pitfall 3: Using Go Home on Web Tests

**Problem:**
```
Test for web application:
1. Navigate to website
2. Go home  ← Not supported, will fail
```

**Solution:**
```
Go Home is mobile-only
For web, use appropriate web navigation (go-back-on-page, exit-last-tab)
```

**Why**: Web browsers don't have a device home screen concept.

### Pitfall 4: Not Testing Return to App

**Problem:**
```
Test: "Background app"
1. Use app
2. Go home  ← Test ends here, doesn't verify return works
```

**Solution:**
```
Test: "Background and return to app"
1. Use app
2. Go home
3. Wait
4. Launch app again
5. Verify app state
6. Continue using app
```

**Why**: The complete user experience includes backgrounding AND returning. Test both.

### Pitfall 5: Ignoring Background Process Interruptions

**Problem:**
```
Test: "Long-running process"
1. Start upload/download
2. Go home
3. Wait: 30 seconds
4. Return
5. Assume: Process completed  ← Process might have paused while backgrounded
```

**Solution:**
```
1. Start upload/download
2. Go home
3. Wait: 30 seconds
4. Return
5. Check: Process status (completed, paused, or failed)
6. Handle each case appropriately
```

**Why**: Background processes may pause, throttle, or fail. Test actual behavior.

### Pitfall 6: Not Testing Permission Changes

**Problem:**
```
1. App has location permission
2. Go home
3. User revokes location permission (not tested)
4. Return to app
5. Assume: Location still working  ← Fails because permission revoked
```

**Solution:**
```
Test permission changes while backgrounded:
1. App has permission
2. Go home
3. Change permission via settings
4. Return to app
5. Verify: App handles permission change correctly
```

**Why**: Users can change permissions while app is backgrounded. Apps should handle this.

## Comparison with Similar Interactions

### Go Home vs Go Back On Page

**Go Home:**
- Platform: Mobile only
- Action: Go to device home screen
- Result: App backgrounds, home screen appears
- App state: App remains in memory
- Best for: Mobile device navigation

**Go Back On Page:**
- Platform: Web only
- Action: Navigate backward in browser history
- Result: Previous page loads in browser
- App state: N/A (browser context)
- Best for: Web browser history navigation

**Relationship**: These are platform-specific equivalents. Go Home for mobile, Go Back for web.

### Go Home vs Exit Last Tab

**Go Home:**
- Platform: Mobile
- Action: Background app to home screen
- Tab concept: Not applicable (mobile apps)
- App state: App remains running
- Best for: Mobile app backgrounding

**Exit Last Tab:**
- Platform: Web
- Action: Close browser tab
- Tab concept: Closes current tab
- App state: Tab closes, previous tab becomes active
- Best for: Web multi-tab navigation

**Relationship**: Different concepts for different platforms. Not interchangeable.

### Go Home vs Killing/Closing App

**Go Home:**
- Action: Background the app
- App process: Continues running
- Memory: Preserved (until OS reclaims)
- State: Maintained
- Return: Fast (app already in memory)

**Kill/Close App:**
- Action: Terminate the app
- App process: Stops completely
- Memory: Released
- State: Cleared (unless saved)
- Return: Slower (cold start)

**When to switch**: Go Home tests normal backgrounding. App killing tests cold start recovery.


## Platform-Specific Considerations

### Android

**Back Button vs Home Button:**
- Back button: May close activity or navigate within app
- Home button (Go Home): Always backgrounds entire app

**Recent Apps:**
After going home, users can access recent apps menu to switch apps.

**Background Restrictions:**
Android may restrict background activity for battery optimization. Test behavior under these conditions.

### iOS

**Swipe Up Gesture:**
On devices without physical home button, swipe up gesture goes home. Go Home simulates this.

**App Switcher:**
After going home, users can open app switcher to see recent apps.

**Background App Refresh:**
iOS may limit background refresh. Test that your app handles this correctly.

## Key Takeaways

1. **Mobile-only interaction** - Works exclusively on Android and iOS, not web
2. **Backgrounds the app** - App remains running in memory (doesn't close)
3. **Tests real interruptions** - Simulates users leaving app temporarily
4. **Essential for notifications** - Required for testing push notification flows
5. **State persistence critical** - Apps should preserve user progress when backgrounded
6. **Always test return** - Background + return is the complete cycle
7. **Wait after going home** - Allow time for home screen to appear
8. **Test various durations** - Short vs long backgrounding may behave differently
9. **Verify background processes** - Location, media, uploads should continue
10. **Handle OS behavior** - OS may kill app for memory; test state restoration
