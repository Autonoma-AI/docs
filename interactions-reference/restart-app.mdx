## What is Restart App?

Restart App is an interaction that closes your application completely and then reopens it from scratch, simulating what happens when a user force-quits your app and launches it again. It's the equivalent of swiping away your app from the task switcher and tapping the icon to reopen it.

This interaction is crucial for testing one of the most overlooked aspects of application quality: **does your app properly handle being closed and reopened?**

When Restart App executes, it completely terminates your application process and then launches it fresh from the home screen or app launcher. This means:
- All in-memory state is cleared
- The app goes through complete initialization
- Any data that wasn't persisted is lost
- The app starts from its default entry point

It's the ultimate test of whether your persistence, state management, and initialization logic work correctly.

## Why Restart Testing is Critical

In the real world, users restart apps constantly, often for reasons you might not expect:

**Common restart triggers:**
- User force-quits app when it seems frozen
- System kills app due to memory pressure
- App crashes and user relaunches it
- User closes app and returns hours or days later
- OS terminates background app to free resources
- Device restarts (system updates, battery drain, etc.)
- User switches between many apps and yours gets terminated

Each of these scenarios should result in a smooth restart experience. But without proper testing, you might discover:

**Common restart failures:**
- Authentication state lost (user forced to log in again)
- Form data disappears (user loses their work)
- App crashes on launch
- Incorrect initial screen displayed
- Cached data corrupted or missing
- Onboarding flows repeat unnecessarily
- Deep links stop working
- Push notification state lost

The difference between an app that handles restarts gracefully and one that doesn't is the difference between user trust and user frustration.

## When to Use Restart App

Restart App should be a standard part of your testing strategy. Here's when it's essential:

**Critical test scenarios:**
- **State persistence**: Verify saved data survives restart
- **Authentication**: Confirm logged-in state persists (or properly expires)
- **Form data**: Ensure draft content is preserved
- **App initialization**: Test cold start behavior
- **Cache validity**: Verify cached data loads correctly
- **Session recovery**: Confirm in-progress operations can resume
- **Memory leaks**: Test repeated restart cycles
- **Deep link handling**: Verify links work after restart
- **Notification state**: Ensure notification badges update correctly

**Essential test patterns:**

```
Pattern 1: Data Persistence
1. Create data
2. Restart app ← Does data survive?
3. Verify data present

Pattern 2: Authentication State
1. Log in
2. Restart app ← Does session persist?
3. Verify still logged in

Pattern 3: Draft Recovery
1. Fill form partially
2. Save draft
3. Restart app ← Is draft recovered?
4. Verify form data restored

Pattern 4: Cold Start Performance
1. Restart app ← How long does cold start take?
2. Wait until: App fully initialized
3. Assert: Performance acceptable

Pattern 5: Crash Recovery
1. Trigger error condition
2. App crashes
3. Restart app ← Does app recover?
4. Verify error handled gracefully
```

## How It Works

When you trigger Restart App in a test, here's what happens:

1. **Application Termination**: Autonoma completely closes your application, terminating all processes
2. **Memory Cleanup**: All in-memory state is cleared (just like a real restart)
3. **Launch Trigger**: The app is launched fresh from the home screen/launcher
4. **Initialization**: Your app goes through its complete startup sequence
5. **Navigation**: The app opens to its default entry screen (usually home or last screen depending on state)
6. **Test Continuation**: Your test continues with the restarted app

This mirrors exactly what happens when users force-quit and relaunch your app, or when the system kills and later restarts it.

## Platform Support

**Web**: Full support (page reload and fresh navigation)
**Mobile**: Full support (Android and iOS app restart)

Restart App works across both platforms, but the behavior differs slightly:

**Web restart behavior:**
- Browser tab closes or page reloads
- Session storage cleared
- Local storage persists
- Cookies persist
- Service workers may cache data

**Mobile restart behavior:**
- App process terminates completely
- All memory cleared
- Persistent storage (UserDefaults, SharedPreferences, databases) survives
- Keychain/credential storage survives
- Cache directories may persist depending on implementation

## Best Practices for Restart Testing

### 1. Test Critical Flows with Restart Steps

Add restart steps to your most important user journeys:

**Good:**
```
Authentication flow:
1. Log in
2. Restart app
3. Verify still logged in
4. Perform authenticated action
5. Restart app again
6. Verify session persists
```

**Incomplete:**
```
1. Log in
2. Perform authenticated action
3. Test complete ← Never tested restart persistence
```

### 2. Verify Data Before and After Restart

Always confirm data matches before and after:

**Good:**
```
1. Create item "Test Item"
2. Extract item ID
3. Assert: Item visible
4. Restart app
5. Search for item by ID
6. Assert: Exact same item appears
7. Assert: All properties match
```

**Insufficient:**
```
1. Create item
2. Restart app
3. Assert: An item exists ← But is it the right item?
```

### 3. Test Multiple Restart Cycles

One restart isn't enough—test repeated cycles:

**Good:**
```

4. Restart app again
5. Verify data still intact
6. Restart app third time
7. Verify data persists
```

**Too limited:**
```
1. Create data
2. Restart app once
3. Assume it works forever ← Might not
```

**Comprehensive:**

## Common Pitfalls

### Pitfall 1: Not Waiting for Full Initialization

**Problem:**
```
1. Restart app
2. Immediately assert data present ← App not ready
```

**Solution:**
```
1. Restart app
2. Wait until: App fully loads
3. Wait until: Home screen displays
4. Assert: Data present
```

### Pitfall 2: Testing Only Logged-In Restarts

**Problem:**
```
Always test with authenticated users, never test logged-out restarts
```

**Solution:**
```
Test both states:
- Logged out restart behavior
- Logged in restart behavior
- Session expiration during restart
- Auth token refresh on restart
```

### Pitfall 3: Not Testing Restart Mid-Flow

**Problem:**
```
Only restart at clean breakpoints, never mid-operation
```

**Solution:**
```
Test disruptive restarts:
1. Start filling form
2. Restart app mid-form
3. Verify draft recovery

1. Start upload
2. Restart during upload
3. Verify upload can resume
```

### Pitfall 4: Assuming Restart = Clean State

**Problem:**
```
Expect restart to clear everything like uninstall/reinstall
```

**Reality:**
```
Restart preserves:
- Local databases
- Persistent storage
- Credentials
- Cached files
- User preferences

Restart clears:
- In-memory state
- Runtime variables
- Non-persisted data
```

### Pitfall 5: Not Testing Cross-Platform Restart Differences

**Problem:**
```
Test restart on one platform, assume it works on others
```

**Solution:**
```
Test platform-specific behavior:

iOS:
- App Store restarts
- Background termination
- Memory pressure kills

Android:
- Process death
- Activity recreation
- Don't keep activities setting

Web:
- Page reload
- Tab restoration
- Session storage behavior
```

### Pitfall 6: Ignoring Cold Start vs Warm Start

**Problem:**
```
Only test cold starts (full restart) or only test warm starts (resume)
```

**Solution:**
```
Test both:

Cold start:
1. Kill app completely
2. Wait 10 seconds
3. Restart app
4. Verify full initialization

Warm start:
1. Background app
2. Wait 2 seconds
3. Resume app
4. Verify quick restore
```

### Pitfall 7: Not Testing Failed Restart Recovery

**Problem:**
```
Only test successful restarts, never test corruption or error scenarios
```

**Solution:**
```
Test error recovery:
1. Create corrupted state
2. Restart app
3. Verify graceful error handling
4. Assert: App offers recovery options
5. Assert: Doesn't crash

Test missing data:
1. Delete cached data
2. Restart app
3. Verify fresh data fetch
4. Assert: Handles missing cache
```

## Understanding Restart Behavior

### What Actually Happens During Restart

**Process termination:**
- All running threads stop
- Memory is released
- Network connections close
- Timers and scheduled tasks cancel

**What persists:**
- SQLite databases
- File system data
- UserDefaults/SharedPreferences
- Keychain/Secure Storage
- Cached files (unless cleared)

**What doesn't persist:**
- In-memory variables
- Runtime state
- Temporary data
- Active network requests
- UI state (unless saved)

### Platform-Specific Restart Behavior

**iOS:**
- App delegate lifecycle methods called
- State restoration (if implemented)
- Background URL sessions may continue
- Keychain data persists

**Android:**
- Activity lifecycle methods called
- Process can be killed by system
- Work Manager tasks may continue
- SharedPreferences persist

**Web:**
- Page reload triggers fresh load
- LocalStorage persists
- SessionStorage clears
- Service worker may cache resources

## Key Takeaways

1. **Restart tests resilience** - Verifies your app handles termination and relaunch
2. **Essential for data persistence** - Ensures saved data survives restart
3. **Critical for auth testing** - Confirms session management works correctly
4. **Tests cold start performance** - Measures initialization time
5. **Reveals memory leaks** - Repeated restarts expose resource issues
6. **Verifies draft recovery** - Ensures work-in-progress is preserved
7. **Tests across platforms** - Web and mobile both supported
8. **Combine with other tests** - Restart + offline, restart + auth, etc.
9. **Test multiple cycles** - One restart isn't enough
10. **Test mid-flow restarts** - Users close apps at unexpected times
