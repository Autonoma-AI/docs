## What is Go Offline?

Go Offline is a mobile testing interaction that simulates complete network disconnection by disabling both WiFi and cellular data connections. It's the equivalent of enabling airplane mode or losing all network connectivity—completely cutting off your app's ability to communicate with the internet.

This interaction lets you test one of the most critical aspects of mobile app quality: **how your app behaves when the network disappears**.

In the real world, network connectivity isn't guaranteed. Users experience connection loss constantly—in elevators, subways, parking garages, rural areas, or when they intentionally enable airplane mode. Your app needs to handle these situations gracefully, and Go Offline lets you test exactly that.

## Why Offline Testing is Critical

Consider what happens when a user loses connectivity while using your app:

**Without proper offline handling:**
- Actions silently fail with no feedback
- Data is lost when operations can't complete
- The app freezes or crashes
- Error messages are confusing or absent
- Users abandon the app in frustration

**With proper offline handling:**
- The app detects connectivity loss immediately
- Users see clear "You're offline" messaging
- Actions are queued for later execution
- Local data remains accessible
- Offline functionality continues to work
- When connectivity returns, changes sync automatically

The difference between these experiences is the difference between a professional app and one that feels broken.

## When to Use Go Offline

Go Offline should be a standard part of your mobile testing strategy. Here's when to use it:

**Essential for testing:**
- Offline-first functionality (reading saved content, viewing cached data)
- Data persistence (ensuring local storage works correctly)
- Queue mechanisms (actions that should execute when back online)
- Error handling (appropriate messages when network operations fail)
- Graceful degradation (features that continue working offline)
- Network state indicators (badges, banners, icons showing offline status)

**Critical test patterns:**
- **Create data offline** → Go back online → Verify sync
- **Load content online** → Go offline → Verify cached content accessible
- **Attempt online action offline** → Verify appropriate error handling
- **Queue actions offline** → Go online → Verify actions execute

**Apps that especially need offline testing:**
- Note-taking and productivity apps
- E-commerce and shopping apps
- Social media and content apps
- Messaging and communication apps
- Travel and navigation apps
- Media and entertainment apps
- Finance and banking apps

Essentially, **any mobile app that handles user data** needs offline testing.

## How It Works

When you trigger Go Offline in a test, here's the sequence of events:

1. **Network Disabling**: Autonoma disables both WiFi and cellular data at the system level
2. **Connection Termination**: Active network connections are immediately severed
3. **State Change Notification**: Your app receives network state change events
4. **Offline Mode Activation**: Your app's offline handling logic engages
5. **Local Operation**: The app now operates in offline mode
6. **Test Continuation**: Your test continues with the app disconnected

This simulates exactly what users experience when they lose connectivity or enable airplane mode.

## Platform Support

**Web**: Not supported (web testing happens in consistent network environments; use browser dev tools for throttling)
**Mobile**: Full support (Android and iOS)

Go Offline is mobile-specific because:
- Mobile devices frequently lose connectivity
- Mobile apps need robust offline capabilities
- Mobile users expect offline functionality
- Testing offline scenarios is essential for mobile quality

## Best Practices for Offline Testing

### 1. Test the Complete Offline Lifecycle

Don't just go offline and immediately back online—test realistic offline usage:

**Good:**
```
1. Go offline
2. Perform multiple offline actions
3. Navigate through app
4. Create, update, delete data
5. Close and reopen app
6. Verify persistence
7. Go online
8. Verify sync
```

**Incomplete:**
```
1. Go offline
2. Do one thing
3. Go online
```

### 2. Verify Offline Indicators

Users need to know when they're offline:

**Good:**
```
1. Go offline
2. Wait until: Offline banner appears
3. Assert: Network indicator shows "Offline"
4. Assert: Status bar reflects offline state
5. Assert: Users clearly informed
```

**Insufficient:**
```
1. Go offline
2. Continue test without verifying user feedback
```

### 3. Test Appropriate Error Messages

When online actions fail offline, errors should be clear:

**Good:**
```
1. Go offline
2. Attempt to load new content
3. Assert: "You're offline. Content unavailable." message
4. Assert: Helpful suggestions provided
5. Assert: Retry option available
```

**Poor:**
```
1. Go offline
2. Attempt action
3. Assert: Generic "Error" message ← Unhelpful
```

### 4. Verify Data Persistence Across Restarts

Offline data should survive app restarts:

**Good:**
```
1. Go offline
2. Create data
3. Close app
4. Reopen app
5. Assert: Data still present
6. Assert: Offline state remembered
7. Go online
8. Verify sync
```

**Risky:**
```
1. Go offline
2. Create data
3. Go online
4. Never test restart scenario ← Might lose data
```

### 5. Test Both Graceful Degradation and Hard Failures

Some features should work offline, others should fail gracefully:

**Complete testing:**
```
Features that should work offline:
- View cached content ✓
- Read saved items ✓
- Edit local data ✓
- Use offline features ✓

Features that should fail gracefully:
- Load new content ✗ (clear message)
- Sync changes ✗ (queued for later)
- Real-time features ✗ (explains why unavailable)
```

### 6. Test Queue Mechanisms Thoroughly

If actions queue offline, test edge cases:

**Comprehensive queue testing:**
```
1. Queue multiple actions
2. Verify queue order preserved
3. Test queue size limits
4. Verify queue persistence across restarts
5. Test partial queue failures when online
6. Verify queue retry logic
7. Test queue conflicts
```

### 7. Combine with Other Testing Patterns

Offline testing should integrate with other test types:

**With form testing:**
```
1. Start filling form
2. Go offline
3. Continue filling form
4. Verify draft saves
5. Go online
6. Complete submission
```

**With navigation:**
```
1. Go offline
2. Navigate through app
3. Verify routing works
4. Verify cached pages load
5. Verify new pages show offline message
```

**With data extraction:**
```
1. Go offline
2. Create item
3. Extract item ID
4. Go online
5. Verify item with extracted ID synced
```

## Common Pitfalls

### Pitfall 1: Not Verifying Offline State

**Problem:**
```
1. Go offline
2. Immediately perform actions ← Did offline actually engage?
```

**Solution:**
```
1. Go offline
2. Wait until: Offline indicator appears
3. Assert: App knows it's offline
4. Then perform actions
```

### Pitfall 2: Testing Only Happy Paths

**Problem:**
```
Only test:
- Create one item offline
- Go online
- It syncs successfully
```

**Solution:**
```
Test edge cases:
- Create many items offline
- Update and delete offline
- Conflicts during sync
- Partial sync failures
- Network flapping
- Long offline periods
```

### Pitfall 3: Not Testing Offline Persistence

**Problem:**
```
1. Go offline
2. Create data
3. Go online immediately
4. Never test if data survives app restart
```

**Solution:**
```
1. Go offline
2. Create data
3. Close app
4. Reopen app
5. Assert: Data still there
6. Go online
7. Verify sync
```

### Pitfall 4: Ignoring User Feedback

**Problem:**
```
1. Go offline
2. Test functionality
3. Don't verify users are informed they're offline
```

**Solution:**
```
1. Go offline
2. Assert: Clear offline indicator
3. Assert: Appropriate error messages
4. Assert: Helpful guidance provided
5. Test functionality
```

### Pitfall 5: Not Testing Cross-Device Sync

**Problem:**
```
1. Go offline on Device A
2. Create data
3. Go online
4. Only verify on Device A
```

**Solution:**
```
1. Go offline on Device A
2. Create data
3. Go online
4. Verify sync completes
5. Check Device B
6. Assert: Data appears on Device B
7. Verify consistency across devices
```

### Pitfall 6: Assuming Instant Sync

**Problem:**
```
1. Go offline
2. Create 100 items
3. Go online
4. Immediately assert all items synced ← Fails, sync takes time
```

**Solution:**
```
1. Go offline
2. Create 100 items
3. Go online
4. Wait until: Sync starts
5. Wait until: Progress indicator shows syncing
6. Wait until: All items synced
7. Assert: Sync completed successfully
```

### Pitfall 7: Not Testing Offline Feature Limitations

**Problem:**
```
Test everything as if offline should work identically to online
```

**Solution:**
```
Document and test what SHOULD be limited:
- Real-time features disabled ✓
- New content loading fails gracefully ✓
- Social features show appropriate messages ✓
- Search limited to cached content ✓
```

## Understanding Offline Behavior Patterns

### Pattern 1: Read-Only Offline (Content Apps)

Cache content online, read offline:

```
- News articles
- Podcast episodes
- Video content
- Documentation
- Maps
```

**Test focus**: Cache integrity, playback capability, navigation.

### Pattern 2: Full Offline Functionality (Productivity Apps)

Create and edit offline, sync later:

```
- Note-taking
- Task management
- Document editing
- Drawing/design apps
```

**Test focus**: Data persistence, conflict resolution, sync reliability.

### Pattern 3: Queue-Based Offline (Social Apps)

Actions queue offline, execute when online:

```
- Posting updates
- Sending messages
- Liking content
- Following users
```

**Test focus**: Queue management, execution order, error handling.

### Pattern 4: Graceful Degradation (Hybrid Apps)

Some features work, others disabled:

```
- E-commerce (browse cached, can't checkout)
- Banking (view balance, can't transfer)
- Travel (view bookings, can't book new)
```

**Test focus**: Feature availability, clear communication, smooth degradation.

## Key Takeaways

1. **Go Offline simulates complete network loss** - Tests the worst-case scenario
2. **It's essential for mobile apps** - All mobile apps experience offline conditions
3. **Test complete offline cycles** - Create, persist, sync, verify
4. **Verify user feedback** - Users must know they're offline
5. **Test data persistence** - Offline data must survive app restarts
6. **Queue mechanisms are critical** - Actions must queue and execute when online
7. **Test error handling** - Offline errors should be clear and helpful
8. **Verify cross-device sync** - Changes must propagate everywhere
9. **Test edge cases** - Conflicts, large data sets, rapid toggling
10. **Think offline-first** - Modern mobile apps should work offline by default
