# Extract Information

## The Memory Problem in Testing

Your test completes a checkout flow. The confirmation page displays:

```
Order Confirmed!
Order #A7B3X9
Expected delivery: March 15
Total: $87.49
```

Perfect. Now you need to verify that this order appears in the order history page.

You navigate to order history and... **how do you tell your test which order to look for?**

The order number changes every time the test runs. You can't hardcode "#A7B3X9"—that only works for this specific test execution. Next time it might be "#B2K5M8".

**Tests, by default, have no memory.** They see information, perform actions, and move on. They don't remember what they saw.

This is the fundamental challenge of testing dynamic applications:
- Order numbers are generated
- Confirmation codes are created
- User IDs are assigned
- Invoice numbers are produced
- Booking references are issued

**Your test needs to capture these values and remember them for later verification.**

That's what `Extract Information` does. It gives your tests memory—the ability to capture information from your application and reuse it throughout the test.

## What Extract Information Does

The `Extract Information` interaction captures visual information from your application and stores it under a key name that you can reference later in your test.

Think of it like taking a photo of something important and labeling it so you can find it again.

**Basic syntax**:
```
Extract information about <what to extract> with key <KEY_NAME>
```

**Examples**:
```
Extract information about the order number with key ORDER_ID
Extract information about the confirmation code with key CONFIRMATION_CODE
Extract information about the user email with key USER_EMAIL
Extract information about the balance with key ACCOUNT_BALANCE
Extract information about the booking reference with key BOOKING_REF
```

Autonoma's AI examines your application's current screen, finds the information you described, extracts it, and stores it under the key name you provided.

**Using extracted values**:
Once extracted, you reference the value using `{{key:KEY_NAME}}`:

```
1. Extract information about the order number with key ORDER_ID
2. Navigate to order history
3. Assert: Order {{key:ORDER_ID}} appears in the list
4. Click: Order {{key:ORDER_ID}}
5. Assert: Order details page shows {{key:ORDER_ID}}
```

## When to Use Extract Information vs Other Approaches

Autonoma provides multiple ways to work with data. Here's when to use extraction:

### Use `Extract Information` when:
- **Application generates dynamic values** - Order numbers, IDs, codes, references
- **You need to verify values across pages** - Confirming data appears consistently
- **Values change each test run** - Can't hardcode because values are unique
- **Testing multi-step workflows** - Capturing information from one step to use in another
- **Validating data persistence** - Ensuring values save and reload correctly

**Example scenarios**:
```
Capture order number to verify in history:
Extract information about the order number with key ORDER_ID

Capture confirmation code to check email:
Extract information about the confirmation code with key CONFIRMATION

Capture username to verify in profile:
Extract information about the username with key USERNAME

Capture invoice ID for API validation:
Extract information about the invoice ID with key INVOICE_ID
```

### Use `Variables` when:
- **Values are known before the test runs** - Test credentials, URLs, configuration
- **Values don't change during the test** - Static data you control
- **Same values across multiple tests** - Shared configuration or test data

**Example scenarios**:
```
{{variable:TEST_EMAIL}} - Known test account email
{{variable:APP_URL}} - Application base URL
{{variable:API_KEY}} - API authentication key
```

### Use `Random Data` when:
- **You need unique values for testing** - Autonoma generates them for you
- **Testing registration or creation flows** - Need fresh data each run
- **Values don't need to be extracted** - Generated and used immediately

**Example scenarios**:
```
{{random:email}} - Generates test@example.com format
{{random:first_name}} - Generates realistic first names
{{random:company_name}} - Generates company names
{{random:phone_number}} - Generates phone numbers
```

### The Key Distinction

**Variables** (`{{variable:NAME}}`): You control the value (set before test runs)

**Random data** (`{{random:type}}`): Autonoma controls the value (generates during test)

**Keys** (`{{key:NAME}}`): Your application controls the value (extraction captures it)

**Think of it this way**:
- **Variables**: "I'm logging in as test@example.com" (you decided)
- **Random**: "I'm registering as alice.jones.x7k9@example.com" (Autonoma generated)
- **Keys**: "My order number is #A7B3X9" (your app created, extraction captured)

## Best Practices for Effective Extraction

### 1. Extract Immediately When Values Appear

**Poor timing**:
```
1. Complete checkout
2. Navigate to another page
3. Extract information about order number ← Too late! You left the page
```

**Good timing**:
```
1. Complete checkout
2. Wait until: Confirmation appears
3. Extract information about order number with key ORDER_NUMBER ← Right after it appears
4. Navigate to another page
```

Extract values as soon as they appear on screen.

### 2. Use Descriptive Key Names

**Vague**:
```
Extract information about the number with key NUM
Extract information about the code with key CODE
Extract information about the ID with key ID
```

**Descriptive**:
```
Extract information about the order number with key ORDER_NUMBER
Extract information about the confirmation code with key CONFIRMATION_CODE
Extract information about the user ID with key USER_ID
```

Clear key names make your test easier to understand and maintain.

### 3. Extract Before Navigating Away

Once you navigate away from a page, you can't extract from it:

```
1. View order confirmation
2. Extract information about order number with key ORDER_NUMBER ← Do this BEFORE step 3
3. Click: "Continue Shopping"
4. Navigate to products
```

### 4. Extract Multiple Related Values

When related data appears together, extract all of it:

```
On order confirmation:
1. Extract information about the order number with key ORDER_NUMBER
2. Extract information about the order total with key ORDER_TOTAL
3. Extract information about the order date with key ORDER_DATE
4. Extract information about the delivery estimate with key DELIVERY_DATE
```

This allows comprehensive validation later.

### 5. Be Specific About What to Extract

**Vague**:
```
Extract information about the number with key NUM
```

**Specific**:
```
Extract information about the order number with key ORDER_NUMBER
```

The more specific your description, the more reliably Autonoma can find and extract the correct value.

### 6. Handle Empty Values Appropriately

The interaction documentation notes: "In case the value is empty or has no value just return an empty string."

**Example**: Extracting from an empty input field:
```
1. Navigate to profile
2. Extract information about the middle name with key MIDDLE_NAME
```

If the middle name field is empty, the key will contain an empty string. Your test should handle this:

```
3. If {{key:MIDDLE_NAME}} is not empty:
4.   Assert: Middle name appears in header
5. Otherwise:
6.   Assert: Middle initial not displayed
```

### 7. Verify Extraction Succeeded

After extracting, immediately verify the value makes sense:

```
1. Extract information about the order number with key ORDER_NUMBER
2. Assert: Order number {{key:ORDER_NUMBER}} is displayed
3. Assert: Order number starts with "#"
```

This confirms extraction worked before you rely on the value later.

### 8. Use Keys in Assertions for Robust Testing

**Fragile**:
```
Assert: Order appears in list
```

**Robust**:
```
Assert: Order {{key:ORDER_NUMBER}} appears in list
```

Using extracted keys makes assertions specific to the current test execution.

## Common Pitfalls and How to Avoid Them

### Pitfall 1: Extracting After Navigating Away

**Problem**:
```
1. Complete checkout
2. Click: "Continue Shopping"
3. Extract information about order number ← Page is gone!
```

**Solution**:
```
1. Complete checkout
2. Extract information about order number with key ORDER_NUMBER
3. Click: "Continue Shopping"
```

Always extract before navigation.

### Pitfall 2: Using Keys Before Extraction

**Problem**:
```
1. Navigate to order history
2. Assert: Order {{key:ORDER_NUMBER}} appears ← ORDER_NUMBER doesn't exist yet!
```

**Solution**:
```
1. Complete checkout
2. Extract information about order number with key ORDER_NUMBER
3. Navigate to order history
4. Assert: Order {{key:ORDER_NUMBER}} appears
```

Extract before using.

### Pitfall 3: Vague Extraction Descriptions

**Problem**:
```
Extract information about the ID with key ID
```

**Why it's problematic**: Your page might have multiple IDs (user ID, order ID, product ID, session ID). Which one?

**Solution**:
```
Extract information about the order ID with key ORDER_ID
```

Be specific about which ID to extract.

### Pitfall 4: Not Handling Missing Values

**Problem**:
```
1. Extract information about the coupon code with key COUPON
2. Assert: Coupon {{key:COUPON}} applied ← Fails if no coupon was used
```

**Solution**:
```
1. Extract information about the coupon code with key COUPON
2. If coupon was applied:
3.   Assert: Coupon {{key:COUPON}} shows discount
4. Otherwise:
5.   Assert: No coupon code displayed
```

Account for scenarios where the value might be empty.

### Pitfall 5: Confusing Extraction with Variables

**Problem**:
```
Trying to use {{variable:ORDER_NUMBER}} but it's actually an extracted key
```

**Why it fails**: Variables are set before the test runs. Extracted values are captured during the test.

**Solution**:
```
Use {{key:ORDER_NUMBER}} for extracted values
Use {{variable:TEST_EMAIL}} for pre-set variables
```

### Pitfall 6: Extracting Complex Objects

**Problem**:
```
Extract information about the entire order details object with key ORDER
```

**Why it's problematic**: The interaction extracts visual information, not data structures.

**Solution**:
```
Extract individual pieces of information:
1. Extract information about the order number with key ORDER_NUMBER
2. Extract information about the order total with key ORDER_TOTAL
3. Extract information about the order status with key ORDER_STATUS
```

Extract specific values, not complex objects.

### Pitfall 7: Extracting Non-Visible Information

**Problem**:
```
Extract information about the hidden field value with key HIDDEN_VALUE
```

**Why it might fail**: Extraction works on visible information. Hidden values might not be extractable.

**Solution**: If you need hidden values, use API calls or other inspection methods:
```
1. Make API call: GET /api/order/details
2. Extract information from API response
```

## Debugging Extraction Failures

When extraction fails, you need to determine why the information couldn't be captured.

### Common Failure Scenarios

**Scenario 1: Information Not Found**
```
Step 5: Extract information about the order number with key ORDER_NUMBER
Failed: Could not locate order number on the page
```

**Debugging**:
1. Check the screenshot—is the order number actually visible?
2. Is it displayed differently than described? (Maybe "Order ID" instead of "order number")
3. Did the previous step complete successfully?
4. Is the information in a collapsed section or hidden element?

**Scenario 2: Ambiguous Description**
```
Step 3: Extract information about the code with key CODE
Failed: Multiple code values found on page
```

**Debugging**:
1. Be more specific: "confirmation code" instead of "code"
2. Provide more context: "the confirmation code below the order summary"
3. Check if multiple codes are displayed (promo code, order code, etc.)

**Scenario 3: Timing Issue**
```
Step 7: Extract information about the total with key TOTAL
Failed: Total not yet displayed
```

**Debugging**:
1. Add a wait before extraction: `Wait until: Order total appears`
2. Ensure asynchronous calculations complete before extracting
3. Check if page is still loading

## What's Next

You now understand how to give your tests memory—extracting dynamic information from your application and reusing it throughout your test flows. This unlocks testing of complex, multi-step workflows that involve application-generated values.

Extraction is one of the four fundamental verification techniques in Autonoma:
- **Assert** - Verify visual elements and content exist
- **Assert URL Location** - Validate navigation and routing
- **Math Assert** - Check mathematical calculations
- **Extract Information** - Capture and reuse dynamic data

Together, these interactions give you complete control over test validation—from simple presence checks to complex multi-step workflow verification with data capture and calculation validation.
