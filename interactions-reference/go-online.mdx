## What is Go Online?

Go Online is a mobile-specific interaction that re-enables network connectivity after it has been disabled. Think of it as turning airplane mode off, re-enabling WiFi, or restoring your data connection—bringing your device back to a fully connected state.

This interaction is the counterpart to Go Offline, and together they form a powerful testing duo that lets you simulate the full spectrum of network conditions users experience in the real world.

When you use Go Online, Autonoma restores both WiFi and cellular data connections, returning your test device to normal network operation. This allows you to test how your application recovers from offline states, handles data synchronization, and responds to network restoration.

## Why Network State Control Matters

In the real world, users don't always have perfect network connectivity. They walk through tunnels, enter buildings with poor reception, toggle airplane mode, or experience intermittent connectivity. Your app needs to handle these scenarios gracefully.

Consider these common user experiences:

**Scenario 1: The Subway User**
A user is reading articles in your app during their commute. They go underground, lose signal, then emerge at their stop. When they come back online, they expect:
- Queued actions to process (liked posts, saved articles)
- New content to load seamlessly
- No data loss from their offline interactions

**Scenario 2: The Airplane Mode Toggle**
A user enables airplane mode during a flight, makes changes to their profile offline, then disables airplane mode after landing. They expect:
- Changes to sync automatically
- Conflicts to be handled intelligently
- No duplicate data or errors

**Scenario 3: The Poor Connection Recovery**
A user's app becomes unresponsive due to network issues. They force-close it, check their connection, then reopen the app. They expect:
- The app to detect the restored connection
- Pending operations to resume
- A smooth transition back to normal operation

**Testing these scenarios** ensures your app handles network state changes the way real users expect.

## When to Use Go Online

Go Online should be used whenever you need to restore connectivity during a test flow. Here are the key scenarios:

**Perfect for:**
- Testing recovery from offline mode
- Validating data synchronization when connectivity returns
- Verifying queued actions process correctly after coming back online
- Testing real-time feature behavior when network is restored
- Simulating airplane mode being disabled
- Testing network reconnection flows
- Validating online-only features become available again

**Essential patterns:**
- **Offline → Online transitions**: Test what happens when users regain connectivity
- **Sync validation**: Ensure data created offline syncs when connection returns
- **Queue processing**: Verify pending operations execute after going online
- **Feature availability**: Confirm online-only features re-enable properly

**Test sequence example:**
```
1. Perform actions while online
2. Go offline
3. Attempt offline interactions
4. Go online ← Restore connectivity
5. Verify sync and recovery behavior
```

## How It Works

When you trigger Go Online in a test, here's what happens:

1. **Network Stack Restoration**: Autonoma re-enables both WiFi and cellular data at the system level
2. **Connection Establishment**: The device re-establishes network connections
3. **Application Notification**: Your app receives network state change events
4. **Sync Trigger**: Network-dependent operations can now proceed
5. **Test Continuation**: Your test continues with network connectivity restored

This mirrors what happens when a user manually re-enables their network connections or moves back into coverage.

## Platform Support

**Web**: Not supported (use browser dev tools for network throttling)
**Mobile**: Full support (Android and iOS)

Go Online is specifically designed for mobile testing because:
- Mobile devices frequently experience network state changes
- Mobile apps need offline-first capabilities
- Mobile users toggle airplane mode regularly
- Mobile connectivity is less stable than desktop/web environments

You're testing a note-taking app where users can create notes offline and expect them to sync when they come back online.

```

4. Click: "New Note" button

6. Type "This note was created while online" in content field
7. Click: "Save" button
8. Wait until: Note saves
9. Assert: "Online Note" appears in notes list

10. Go offline
11. Wait until: Network indicator shows "Offline"
12. Assert: Offline mode banner appears
13. Click: "New Note" button
14. Type "Offline Note" in title field
15. Type "This note was created while offline" in content field
16. Click: "Save" button
17. Wait until: Note saves locally
18. Assert: "Offline Note" appears in notes list
19. Assert: Sync pending indicator shows on note

Restore connectivity and verify sync:
20. Go online ← Key step
21. Wait until: Network indicator shows "Online"
22. Wait until: Sync completes
23. Assert: Both notes appear in list
24. Assert: "Offline Note" no longer shows sync pending indicator
25. Assert: Timestamp updated on synced note

Verify persistence:
26. Restart app
27. Wait until: Notes list loads
28. Assert: Both "Online Note" and "Offline Note" are present
29. Assert: Both notes show synced status
```

**Why this matters**: This tests the complete offline-to-online lifecycle that real users experience constantly with note-taking, task management, and content creation apps.

## Best Practices for Network State Testing

### 1. Always Verify State Changes

When you go online, confirm the network state actually changed:

**Good:**
```
1. Go online
2. Wait until: Network indicator shows "Online"
3. Assert: Offline banner disappears
```

**Incomplete:**
```
1. Go online
2. Continue with test ← Might fail if network didn't restore yet
```

### 2. Allow Time for Synchronization

Network restoration doesn't mean immediate sync. Give operations time to complete:

**Good:**
```
1. Go online
2. Wait until: "Syncing..." indicator appears
3. Wait until: Sync completes
4. Assert: Data updated
```

**Too fast:**
```
1. Go online
2. Assert: Data updated ← May fail, sync takes time
```

### 3. Test Complete Offline-Online Cycles

Don't just test going online in isolation—test the full cycle:

**Complete test:**
```
Start online:
1. Perform baseline actions
2. Verify online functionality

Go offline:
3. Go offline
4. Perform offline actions
5. Verify offline behavior

Return online:
6. Go online
7. Wait for sync
8. Verify data integrity
9. Verify no data loss
```

### 4. Handle Intermediate States

Between offline and fully-online, apps often show "reconnecting" or "syncing" states:

**Good:**
```
1. Go online
2. Wait until: Shows "Reconnecting..."
3. Wait until: Shows "Syncing data..."
4. Wait until: Shows "Sync complete"
5. Assert: Fully operational
```

**Oversimplified:**
```
1. Go online
2. Assert: Everything works ← Might catch intermediate error state
```

### 5. Verify Data Integrity

After going online, ensure data created offline is preserved and synced correctly:

**Good:**
```
1. Go online
2. Wait until: Sync completes
3. Assert: Offline data present
4. Assert: Online data present
5. Assert: No duplicates
6. Assert: Correct timestamps
7. Assert: No data corruption
```

### 6. Test with Multiple Offline Actions

Don't just test one offline action—test realistic usage:

**Realistic:**
```
Offline period:
1. Create 3 items
2. Update 2 items
3. Delete 1 item
4. Like 5 posts
5. Send 4 messages

Back online:
6. Go online
7. Wait for all sync operations
8. Verify all changes propagated
```

### 7. Include Cross-Device Verification

When possible, verify synced data appears on other devices:

**Good:**
```
Device 1:
1. Go offline
2. Create data
3. Go online
4. Wait for sync

Device 2:
5. Refresh
6. Assert: New data appears
7. Assert: Changes visible
```

## Common Pitfalls

### Pitfall 1: Not Waiting for Sync

**Problem:**
```
1. Go online
2. Assert: Data synced ← Fails, sync takes time
```

**Solution:**
```
1. Go online
2. Wait until: Sync indicator appears
3. Wait until: Sync completes
4. Assert: Data synced
```

### Pitfall 2: Assuming Instant Connectivity

**Problem:**
```
1. Go online
2. Make API call ← Might fail, connection not fully established
```

**Solution:**
```
1. Go online
2. Wait until: Connection indicator shows "Connected"
3. Wait: 2 seconds (for connection to stabilize)
4. Make API call
```

### Pitfall 3: Not Testing Sync Conflicts

**Problem:**
```
Only test simple offline→online scenarios with no conflicts
```

**Solution:**
```
Test conflict scenarios:
1. Modify same item offline on two devices
2. Go online on both
3. Verify conflict resolution
4. Assert: App handles conflicts gracefully
```

### Pitfall 4: Ignoring Network Error Recovery

**Problem:**
```
1. Go online
2. Assume everything works perfectly
```

**Solution:**
```
1. Go online
2. Wait for sync attempt
3. If errors occur, verify retry logic
4. Assert: Error messages are clear
5. Assert: Manual retry option available
```

### Pitfall 5: Testing Only Perfect Scenarios

**Problem:**
```
Only test:
- Go offline
- Perform one action
- Go online
- Success
```

**Solution:**
```
Test realistic complexity:
- Multiple offline actions
- Partial sync failures
- Network flapping (on/off/on)
- Large data sets
- Concurrent users
- Edge cases
```

### Pitfall 6: Not Verifying Backend State

**Problem:**
```
1. Go online
2. Assert: UI shows synced
3. Test complete ← Didn't verify backend actually received data
```

**Solution:**
```
1. Go online
2. Assert: UI shows synced
3. Make API call to verify backend state
4. Assert: Data actually persisted server-side
```

## Understanding Network State in Mobile Testing

### What "Online" Actually Means

When you trigger Go Online, you're restoring:

**WiFi connectivity:**
- Connection to local network
- Internet access via WiFi
- Higher bandwidth operations possible

**Cellular data:**
- Mobile network connection
- Fallback when WiFi unavailable
- Potentially metered connection

**Both connections allow:**
- API calls to succeed
- WebSocket connections to establish
- Real-time updates to flow
- Media downloads to proceed
- Push notifications to be received

### Network State Events Your App Receives

When connectivity is restored, your app typically receives:

1. **Connection state change events** - System notifies app of network availability
2. **Reachability notifications** - App detects internet is accessible
3. **Background sync triggers** - OS may trigger pending sync operations
4. **WebSocket reconnection** - Real-time connections re-establish
5. **Push notification registration** - Notification services reconnect

Your tests should account for the time these operations take.

## Comparison with Alternatives

### Go Online vs Manual Network Configuration

**Go Online (Autonoma):**
```
1. Go online
2. Network immediately restored
3. App receives state change events
4. Test continues
```

**Manual approach:**
```
1. Access device settings
2. Navigate to network settings
3. Toggle WiFi on
4. Toggle cellular data on
5. Wait for connections to establish
6. Return to app
7. App may need refresh
```

**Why Go Online is better**: It's instant, reliable, and doesn't require navigating away from your app.

### Go Online vs Waiting for Network Recovery

**Proactive approach:**
```
1. Go online (controlled timing)
2. Wait for known state change
3. Verify sync behavior
```

**Passive approach:**
```
1. Wait for network to randomly return
2. Hope timing is right for test
3. Results unpredictable
```

**Why control is essential**: Testing requires reproducibility. Going online on command ensures consistent test execution.
